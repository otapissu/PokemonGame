02 데이터 설계
2-1. ScriptableObject 활용

데이터와 로직을 분리하기 위해 두 종류의 ScriptableObject를 사용한다.

ScriptableObject 역할 주요 필드
PokemonData 포켓몬 원본 정보 id, pokemonName, canHatch, isLegendary, genderVisualType, maleRatio, evolutionOptions[]
EggBalanceData 강화 밸런스 수치 successRates[], destroyRates[], enhanceCosts[], sellPrices[], reviveCosts[]
설계 포인트

ScriptableObject로 분리함으로써 코드 변경 없이 인스펙터에서 밸런스 수치를 조정할 수 있다.

2-2. 런타임 인스턴스 데이터 — PokemonInstance
rootData
최초 부화 시 포켓몬 (진화 후에도 불변 유지)
data
현재 진화 상태의 PokemonData
enhanceLevel
강화 단계 (1~15)
gender
Male / Female / None
isShiny
이로치 여부
formIndex
현재 폼 인덱스 (0부터 시작)
Note

rootData는 진화 후에도 불변으로 유지되어 진화 체인 역추적에 사용된다.

03 주요 시스템
3-1. 부화 시스템

포켓몬을 랜덤으로 부화시킨다. 인벤토리 아이템(향로, 빛나는 부적)을 미리 리스트에 담아 부화 결과에 영향을 줄 수 있다.

설계 포인트

부화 로직은 EggHatchService 단일 책임으로 분리 (Controller와 분리). 아이템 효과는 부화 직전 상태를 읽고, 부화 완료 후 일괄 소비.

Hatch() 1. 파괴 상태 초기화 (IsDestroyed = false, UpdateDestroyedUI()) 2. 리스트에 담긴 아이템 상태 읽기 (향로, 빛나는 부적) 3. 포켓몬 부화 - 5% 확률 전설 / 95% 일반 구분 후 균등 랜덤 - 향로 활성화 시 genderVisualType == None 제외 4. 성별 롤 → maleRatio 반영 (향로 사용 시 고정) 5. 이로치 판정 → 기본 2%, 빛나는 부적 사용 시 10% 6. 폼 결정 → PokemonFormUtility.GetRandomFormIndex() 7. PokemonInstance 생성, 저장, 도감 등록 8. 선택 아이템 일괄 소비 (ApplySelectedItems)
폼 결정 방식
GetAvailableFormIndices(data, gender, isShiny): for i in 0..10: if Resources.Load("Pokemon/{id}_{normal|shiny}[_m|_f][_{i}]") 존재: result.Add(i) else: break // 중간에 없으면 탐색 중단 return result // 가중치 없음 → 모든 폼 균등 확률
3-2. 강화 시스템

골드를 소비하여 강화를 시도한다. 단계마다 성공 파괴 실패 세 가지 결과가 있으며, 파괴된 포켓몬은 아이템으로 되살릴 수 있다.

설계 포인트

EggEnhanceController는 UI 상태 보관, 실제 로직은 EggEnhanceService로 위임. 밸런스 수치는 EggBalanceData ScriptableObject에서만 관리.

강화 성공률 계산
effectiveRate = EggBalanceData.successRates[nextLevel] + (강화 보너스 아이템 장착 시 +0.05) clamp(0, 1)
구현 흐름
Enhance(): 비용 부족 시 → 실패 메시지 리턴 gold -= cost roll = forceSuccess ? 0f : Random.value // #if UNITY_EDITOR 테스트 토글 if roll < successRate → HandleSuccess() elif roll < successRate + destroyRate → HandleDestroyed() else → 실패 메시지
파괴 / 복구 버튼 구조

파괴와 복구는 버튼을 분리하여 관리한다. 파괴 시 강화하기 버튼은 Y위치가 내려가고 되살리기 버튼이 노출된다.

// 파괴 시 DestroyedSnapshot = RevivalSnapshot(currentInstance) currentInstance = null IsDestroyed = true UpdateDestroyedUI() // 강화버튼 Y -= 140, 되살리기버튼 활성화 // 강화하기 버튼: 파괴 상태 무시, 새 포켓몬 부화 // 되살리기 버튼: 기력의 덩어리 아이템 선택 후 누르면 복구 // 복구 시 복구권 갯수 확인 (강화 단계에 따라 비용 차등) currentInstance = RevivalSnapshot으로부터 복원 IsDestroyed = false UpdateDestroyedUI() // 강화버튼 원위치, 되살리기버튼 비활성화 // 새 포켓몬 부화 시에도 UpdateDestroyedUI() 호출 → 버튼 원위치
판매가 계산
sellPrice = balanceData.sellPrices[enhanceLevel] × (전설 시 × 1.5) × (이로치 시 × 2.0) ÷ (아이템 진화 조건을 충족했으나 아이템 없이 미진화 시 ÷ 2)
3-3. 진화 시스템

강화 성공 시 자동으로 진화 조건을 판단한다. 진화 조건은 강화 단계(Level) 아이템(Item) 두 가지 방식이 있으며 EvolutionOption 배열로 정의한다.

설계 포인트

진화 로직은 PokemonEvolutionService로 완전 분리. 다중 진화 분기를 배열 구조로 표현하여 코드 변경 없이 데이터만으로 신규 진화 추가 가능.

EvolutionOption 구조
targetData
진화 후 PokemonData
method
Level / Item
requiredItem
필요 아이템 (Item 방식만)
requiredEnhanceLevel
진화 조건 강화 단계
requiredSourceFormIndex
조건 폼 인덱스 (-1이면 무조건)
targetFormIndex
진화 후 폼 인덱스 (-1이면 무작위)
진화 탐색 흐름
GetRandomAvailableEvolution(instance): 후보 = [] for option in instance.data.evolutionOptions: if enhanceLevel < option.requiredLevel → skip if formIndex 불일치 → skip if method == Item and !inventory.HasItem(option.requiredItem) → skip 후보.Add(option) return 후보 중 랜덤 1개 // 아이템 진화 성공 후 PlayerEvolveInventory.ConsumeItem(option.requiredItem) EvolveBagPanelController.Instance?.ClearSelection() // 잔여 수량과 무관하게 선택 해제
Note

진화 타이밍(아이템 미선택)에서 강화 버튼을 누르면 첫 클릭은 경고 메시지를 표시하고, 두 번째 클릭에서 강화가 진행된다. _pendingEvolveWarning 으로 관리.

3-4. 도감 시스템

부화·강화 이벤트마다 포켓몬 정보를 등록한다. 소유 여부, 폼 목격 여부, 최대 강화 달성 여부를 분리 관리하며 도감 슬롯 아웃라인에 반영한다.

설계 포인트

상태를 HashSet 여러 개로 분리 관리 → 조합 조회가 O(1). 폼 키 형식 통일로 어느 시스템에서든 동일한 키로 조회.

폼 상태 키 형식
기본: "{id}_{M|F}_{formIndex}" 이로치: "S{id}_{M|F}_{formIndex}" 성별 없음: "{id}_N_{formIndex}"
등록 시점
이벤트등록 메서드
부화 완료RegisterPokemon() + RegisterFormSeen()
강화 성공RegisterFormSeen()
15강 달성RegisterMaxEnhance() + PropagateMaxEnhanceToChain()
15강 체인 전파 (별 스프라이트)
PropagateMaxEnhanceToChain(rootData, currentId, currentData, gender, formIndex, isShiny): ancestors = CollectAncestors(rootData, currentId) for ancestor in ancestors: if genderVisualType == DifferentVisual: // 최대강화 포켓몬의 성별만 키 등록 genderMaxKeys.Add(MakeGenderKey(ancestor.id, gender, fi, isShiny)) elif genderVisualType == SameVisual: // 시각적으로 동일 → 암수 양쪽 모두 키 등록 if hasMale: genderMaxKeys.Add(MakeGenderKey(ancestor.id, Male, fi, isShiny)) if hasFemale: genderMaxKeys.Add(MakeGenderKey(ancestor.id, Female, fi, isShiny)) else: // None genderMaxKeys.Add(MakeGenderKey(ancestor.id, None, fi, isShiny)) // SameVisual 버그 수정: 암수 모두 등록하지 않으면 한쪽 성별에만 별이 뜨는 문제 발생
도감 슬롯 아웃라인 상태
  • 미소유 → 검은색 실루엣
  • 소유 → 검은색 기본 아웃라인
  • 체인 일부 15강 → 실버 아웃라인
  • 체인 전체 15강 → 골드 아웃라인
  • 전설 일부 15강 → 골드 아웃라인
  • 전설 전체 15강 → 보라색 아웃라인
ESC 동작

도감 열린 상태에서 ESC → 상세 페이지가 열려 있으면 상세 페이지 먼저 닫기, 없으면 도감 닫기. DexPanelController.Update()에서 CloseDex()를 호출하며 내부에서 분기 처리.

3-5. 인벤토리 시스템

일반 아이템(강화 보조, 부화 보조)과 진화 아이템을 독립적으로 관리한다. 부화 전 적용할 아이템을 미리 선택하여 결과에 영향을 준다.

설계 포인트

PlayerInventoryBase 추상 클래스로 Save/Load/이벤트 공통화. OnChanged 이벤트로 UI가 인벤토리 변경을 구독 → 직접 참조 없이 갱신.

이벤트 기반 UI 갱신 구조
PlayerInventoryBase OnChanged (event Action) ← AddItem / RemoveItem 시 발생 ↓ EvolveBagPanelController.RefreshSlots() 구독 ShopInfoPageController.UpdateOwnedCountText() 구독 ← 실시간 보유 수량 반영
선택 시스템 (일반 가방)
슬롯 클릭 → selectedSlots에 추가 배타 그룹(exclusiveGroupId): 같은 ID 중복 시 기존 제거 후 신규 추가 UsageCondition: 현재 상태와 사용 불가 시 선택 불가 부화 시: ApplySelectedItems() → 선택 아이템 소비 + 선택 초기화 강화 시: ConsumeEnhanceItems() → 강화 보너스 아이템 소비 복구 시: HasRevivalItemSelected() 확인 후 Revive() 호출
저장 방식
// JSON 직렬화 → PlayerPrefs 저장 [{ "itemName": "이로치참", "count": 3 }, ...]
3-6. 상점 시스템

아이템을 구매할 수 있다. 아이템 아이콘을 누르면 상세 페이지가 토글되며 수량 조정 후 구매한다.

ESC 동작

상점 열린 상태에서 ESC → 상세 페이지가 열려 있으면 먼저 닫기(ShopInfoPageController.HideInfo()), 없으면 상점 닫기. ShopPanelController.Update()에서 처리.

실시간 보유 수량 갱신
// ShopInfoPageController.Start()에서 구독 PlayerGeneralInventory.Instance.OnChanged += OnInventoryChanged PlayerEvolveInventory.Instance.OnChanged += OnInventoryChanged // 아이템 구매 → OnChanged 발생 → ownedCountText 즉시 갱신 // 닫았다 열지 않아도 실시간 반영
04 공통 설계 패턴
4-1. Controller → Service 분리

EggEnhanceController는 UI 상태(gold, currentInstance, 이미지 등)만 보관하고, 실제 로직은 Service 클래스에 위임한다.

EggEnhanceController → EggEnhanceService.Enhance(c) → EggHatchService.Hatch(c) → EggUIService.UpdateAll(c) → EggSaveService.Save(c)
Note

Controller를 파라미터로 넘기는 방식으로 Service가 Controller의 필드에 접근한다. Service는 상태를 직접 보관하지 않아 재사용 가능하다.

4-2. Static Utility 분리

폼/스프라이트 경로 계산(PokemonFormUtility)과 밸런스 데이터 조회(EggDataService)는 Static으로 분리하여 어느 클래스에서든 인스턴스 없이 호출 가능하다.

4-3. Singleton 적용 범위

게임 내 단일 존재가 보장되어야 하는 시스템에만 Singleton을 적용한다.

범위대상
영구 존재 DontDestroyOnLoad SoundManager
씬 내 단일 존재 EggEnhanceController, PokedexSaveManager, PlayerGeneralInventory, PlayerEvolveInventory, TutorialManager 등
4-4. Coroutine 기반 애니메이션

Update 루프 대신 Coroutine으로 애니메이션을 처리하여 불필요한 매 프레임 연산을 방지한다.

애니메이션방식
패널 슬라이드EaseInCubic / EaseOutCubic
포켓몬 프레임 애니메이션WaitForSeconds(frameDelay)
메시지 페이드 효과알파 단위 WaitForSeconds
이로치 이펙트Animator 재생 후 자동 비활성화
경고 UI 페이드인/아웃CanvasGroup.alpha 보간
4-5. ESC 키 계층 처리

각 패널의 Update()에서 독립적으로 ESC를 감지하며, 열린 패널이 없으면 무시된다.

DexPanelController.Update(): ESC → CloseDex() ↳ DexInfoController 열려있으면 → HideInfo() 먼저 ↳ 없으면 → SlideDown() ShopPanelController.Update(): ESC → ShopInfoPageController.IsInfoOpen ? HideInfo() : CloseShop() ShopInfoPageController.Update(): ESC → HideInfo()

모든 데이터는 PlayerPrefs에 저장한다.

시스템형식비고
강화 상태int / string 개별 키gold는 long → string 변환
도감쉼표 구분 문자열id 또는 폼 키 목록
인벤토리JSON 배열itemName + count
설정float / int음량, 해상도 인덱스

06 스프라이트 로드 규칙

Resources.LoadAll<Sprite>(path)를 사용하며 경로 규칙은 다음과 같다.

기본: Pokemon/{id}_normal 이로치: Pokemon/{id}_shiny 성별 구분: Pokemon/{id}_normal_m / _f 폼 인덱스: Pokemon/{id}_normal_1 / _2 ... 조합 예시: Pokemon/025_shiny_f_2
폼 탐색 규칙

인덱스 0부터 순차적으로 파일 존재 여부를 확인하며, 중간에 파일이 없으면 탐색을 중단한다. 별도의 폼 목록 데이터가 없고 파일 존재 여부 자체가 폼 정의이다.

07 자료구조 활용

각 자료구조는 그 특성에 맞는 상황에 사용된다.

7-1. Array (배열) T[]

크기가 고정되어 있고 인스펙터에서 할당하거나 런타임에 일괄 로드하는 데이터에 사용한다. 요소 추가/삭제가 없고 인덱스 접근만 필요할 때 가장 적합하다.

위치필드 / 반환값이유
EggBalanceData successRates[], destroyRates[], enhanceCosts[], sellPrices[], reviveCosts[] 강화 단계(1~15)에 1:1 대응하는 고정 수치. 인스펙터에서 직접 편집, 런타임 중 변경 없음
PokemonData evolutionOptions[] 한 포켓몬의 진화 경로는 설계 단계에 고정. 배열 인덱스로 분기 탐색
GeneralBagPanelController GeneralBagSlotUI[] slots 씬에 배치된 UI 슬롯 수는 고정. Inspector에서 드래그로 연결
EggHatchService.LoadSprites() Sprite[] (반환값) Resources.LoadAll<Sprite>(path)가 배열 반환. 로드 후 순차 재생만 하므로 추가 불필요
// balanceData.successRates[nextLevel] — 인덱스로 즉시 접근 float rate = c.balanceData.successRates[nextLevel]; // Resources.LoadAll → Sprite[] 반환, 프레임 루프에서 순서대로 재생 Sprite[] frames = Resources.LoadAll<Sprite>(path); c.pokemonImage.sprite = frames[index % frames.Length];
7-2. List<T> 동적 배열

런타임에 크기가 변하거나 조건에 따라 필터링한 임시 결과를 담을 때 사용한다. 이 프로젝트에서 가장 많이 쓰이는 자료구조이며, "선택 목록" 개념도 List로 구현한다.

위치필드 / 변수역할
EggEnhanceController List<PokemonData> allPokemons 런타임에 Resources.LoadAll<PokemonData>로 전체 포켓몬을 동적 수집
GeneralBagPanelController List<GeneralBagSlotUI> selectedSlots 부화/강화 전 적용할 아이템 슬롯 선택 목록 보관. Add/Remove/Contains를 활용한 선택 동작
PlayerInventoryBase List<InventoryEntry> entries 보유 아이템 목록. 아이템 추가·차감 시 수시로 변경

7-3. Queue<T> FIFO

강화 결과 메시지(성공 · 실패 · 파괴 · 진화)는 한 번의 강화에서 여러 개가 동시에 발생할 수 있다. 먼저 생긴 메시지부터 순서대로 표시해야 하므로 Queue<T>가 적합하다.

위치필드역할
EggEnhanceController Queue<(string msg, Color color)> _messageQueue 강화 결과 메시지를 순서대로 보관. 코루틴이 하나씩 꺼내 표시
// 메시지 추가 _messageQueue.Enqueue((msg, color)); _skipCurrent = true; if (_messageFade == null) _messageFade = StartCoroutine(ProcessMessageQueue()); // 코루틴 — 큐가 빌 때까지 순서대로 표시 while (_messageQueue.Count > 0) { (string msg, Color color) = _messageQueue.Dequeue(); messageText.text = msg; _skipCurrent = false; while (elapsed < 2.0f && !_skipCurrent) { elapsed += Time.deltaTime; yield return null; } }
설계 포인트

버튼을 누르면 _skipCurrent = true로 현재 대기 루프를 즉시 탈출하고 다음 메시지로 전환한다. 마지막 메시지만 2초 표시 후 페이드 아웃된다.
